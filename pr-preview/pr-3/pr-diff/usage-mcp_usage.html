182### Build a reusable suite (author it — there's no save tool)
183
184The MCP has no recording/save/replay tools on purpose: you already know the
185keywords you called and their args, so you can author an optics project directly.

1871. Read the **`optics://project-format`** resource — it documents the CSV layout
188 (`test_cases/`, `modules/`, `test_data/elements.csv`, `config.yaml`), how
189 modules reference `${variables}`, and the escaping rules.
1902. Write those files (the keyword *display names* come from the `optics://keywords`
191 catalog). Parameterize by putting run-specific values in `elements.csv` and
192 referencing them as `${name}`, so "set alarm to 22:00" becomes a reusable
193 `${time}`. A whole cell must be exactly `${name}` — the runner substitutes
194 whole values only, not `${name}` inside a larger string.
1953. For loops, branching, computed values or API calls in a suite, author the
196 control-flow keywords (`Run Loop`, `Condition`, `Evaluate`, `Invoke Api`, …)
197 into the modules — they run under `optics execute`. Live, you drive that logic
198 yourself; they are in the `optics://keywords` catalog but are not one-shot MCP
199 tools because they need the runner's module/data context.
2004. Optionally lint it first: the
201 [optics-framework-lsp](https://github.com/mozarkai/optics-framework-lsp) language
202 server (`uv tool install optics-framework-lsp`) reports every problem in a suite in
203 one pass with `optics-lsp lint <folder> --json`. Its VS Code and JetBrains
204 extensions also offer it to agents as a separate MCP server, `optics-lsp`.
2055. Run it with the CLI: `optics execute <folder>` (results land in
206 `execution_output/`). To replay interactively instead, just call the keyword
207 tools again in sequence — the agent is the runner.
